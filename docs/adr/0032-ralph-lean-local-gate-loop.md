# ADR-0032: Ralph lean loop — local landing under a fast gate, continuous persistence, checkpointed full gate

## Status
Accepted — amends [ADR-0005](0005-ralph-two-frontends-one-policy.md) (the verification points), [ADR-0010](0010-ralph-field-revision.md) (the CI-wait discipline), [ADR-0022](0022-ralph-campaign-revision.md) (the loop-owned merge gate and the per-ticket PR), and [ADR-0028](0028-hosted-session-designated-branch-target.md) (the invariants that survive an engine swap); supersedes [ADR-0027](0027-ralph-gate-ci-wait-repoll.md) and [ADR-0030](0030-ralph-ci-wait-cheap-watcher.md) (the per-ticket CI wait they optimized no longer exists).

## Context
ADR-0022 gave the loop a per-ticket **merge gate**: an implementer opens a PR against the integration base, a gate agent waits for cloud CI and squash-merges through the API, a verifier confirms the merge on the remote. ADR-0027 and ADR-0030 then spent two revisions making that CI wait cheaper (re-poll in place; small-model watchers), because a dispatched subagent cannot idle-wait and the workflow script has no timer.

A fifteen-ticket overnight campaign on a consuming project produced the data both of those ADRs said would trigger a rethink. Every ticket landed, verified, nothing bad reached the default branch — the correctness model held. But the run took ~14.5 hours of wall-clock for roughly 5–6 hours of build-and-verify work; the remaining ~8 hours were overhead, in this order:

- **The cloud-CI wait dominated.** The repository's one required check runs the full monorepo suite including ~150 browser journeys: 13–33 minutes per PR, paid fifteen-plus times — and largely redundant, since the implementer had already run the identical `verify` locally before opening the PR, and the same gate runs in the container in ~5 minutes cold or seconds on warm caches.
- **In-flight work was not persisted.** Implementers work in an isolated worktree and push once, at PR-open. The hosted container was recycled about five times during the run; each recycle before a PR existed threw away whole builds — one ~80-minute window produced zero merges, and three tickets were built more than once.
- **Every relaunch re-paid preflight** (sync + install + the full gate, ~7–11 minutes) to re-prove a base the previous run had already verified.
- **False timeouts** — the gate's re-poll budget was shorter than the slow CI, so green tickets "failed", burned a retry, and re-gated.
- **Parallel migration tickets collided** on the next migration number; the self-healing renumber produced a real regression, a park, and a solo retry.
- **The full suite ran up to four times per ticket** (implementer gate, cloud CI, release verification, close-out).
- Round-shaped dispatch let one 98-minute ticket hold the round while the other slots idled, and a silent journal during a long build was indistinguishable from a hang.

The supervisor's own conclusion was the right one: the correctness model (fresh context per ticket, a gate before every merge, remote-verified completion, consolidation onto one branch) is sound and worth keeping; what is wrong is *where* the gate runs and *when* work is persisted. ADR-0028 had explicitly rejected a "local consolidation" engine — worktree-isolated implementers merged locally, no per-ticket PRs — on the grounds that "per-ticket CI and PR history would be lost for nothing". The field data supplies the missing "for something": the per-ticket cloud-CI round-trip is the single largest cost in the loop and buys nothing the local gate does not already prove.

## Decision
Replace the per-ticket PR-and-CI merge gate with a **local landing**, keep everything else, and persist work continuously. One engine, one shape (ADR-0022) — this is not a second mode beside the old one; the workflow script and the skill's policy block change together.

- **Builders push from the first commit on.** An implementer pushes its `ralph/<n>-<slug>` branch the moment it branches and after every green step (`launch-ralph-implement` owns the cadence). Preflight lists the remote's `ralph/*` branches; a ticket that already has one is dispatched with the branch named so the builder adopts it at its last commit. A retry adopts the branch and fixes forward. A lost container therefore costs the minutes since the last push, never a build, and the pushed branch doubles as the liveness signal a supervisor can read from the remote.
- **The loop lands each finished branch itself, locally, under the fast gate.** A per-ticket **lander** (the orchestrator in skill mode) fetches, fast-forwards the base in the checkout the run was launched from, squash-merges the branch, runs `launchrail verify --fast` on the merged tree, pushes the base, confirms the remote tip, closes the issue explicitly, and leaves one comment naming the landing commit. Lands are strictly serialized (a promise-chain lock in the workflow), so merge ordering needs no remote arbitration. No per-ticket PR is opened; the campaign is released by the one PR the run offers, which is also where cloud CI runs — once. The lander never writes code: a conflict or a red gate is handed back.
- **Land hand-backs spend no attempt.** When the base moved under a finished branch — the squash conflicts, the merged tree fails the gate although the branch was fine on its own, or the remote base kept moving — a fresh implementer re-syncs the pushed branch (`resyncs`, default 2) before the ticket counts as failed. A gate that fails on a branch that already contained the base tip is the builder's failure and spends the attempt.
- **Two verification tiers.** `launchrail verify --fast` runs `testing.checkCommand` — a new optional manifest key for a lint/typecheck/quick-unit gate — falling back to the unit command, never e2e. The full `launchrail verify` (unit + e2e) runs at preflight, at **checkpoints** (every `checkpointEvery` lands, default 5, inside the land lock so nothing interleaves), and at release unless the last green checkpoint already proved the final tip. The full suite is paid once per checkpoint instead of once per ticket, and a red checkpoint has at most `checkpointEvery` suspects.
- **A red checkpoint gets exactly one repair.** The loop dispatches one fresh implementer with the failures and the tickets landed since the last green base; its `ralph/repair-*` branch lands under the *full* gate and becomes the new green checkpoint. If it does not land, the base is red: nothing else lands, finished tickets are **held** on their pushed branches, and the run ends unverified naming the reason. A human fixes the base and relaunches; the held branches are adopted.
- **Preflight honors a known-green base.** A `knownGreen: "<sha>"` arg lets a relaunch skip the full gate when the base tip still equals a sha a previous run verified (sync and install still run). The supervisor passes it from the last recap or journal.
- **A work pool replaces rounds.** The workflow keeps `width` builders busy continuously and lands each branch as it arrives; a slow ticket never holds the others. The frontier dispatches the ticket with the most transitive dependents first (computed from the parsed edges), and keeps **one migration-adding ticket in flight at a time** from a `migration` flag the graph reader reports — the collision that broke a ticket in the field is prevented rather than healed. `maxBuilds` (default 60) replaces `maxRounds` as the backstop; `gateWaits` is gone.
- **Unchanged:** fresh context per ticket; the deterministic frontier from verbatim `Blocked by` lines; deferrals; attempts and parking; the per-ticket remote verifier (a landing commit on the base and a closed issue — the loop still trusts no report); consolidation by default with the release PR offered, never opened; the hosted-session target rule; the unattended-launch guard; the recap contract.

## Alternatives considered
- **Keep the PR-and-CI gate and only add continuous pushes.** Fixes the lost-work cost but leaves the dominant one — 13–33 minutes of cloud CI per ticket, plus the watcher machinery of ADR-0027/0030 to wait it out. Rejected: the local gate is the same gate, minutes instead of tens of minutes, and needs no waiting at all.
- **Land unverified and react when the consolidation branch's CI fails** ("build, merge, build, merge"). Rejected: with parallel builders several suspect lands pile up between failures and the loop is bisecting instead of localizing; the gate *before* the land is what kept one ticket's regression from poisoning the fourteen others' bases in the field run. The checkpoint-plus-one-repair mechanism is the bounded version of "react when the branch fails".
- **Have the implementer land its own branch** (compare-and-swap on the base). Rejected: two ownership models is two failure surfaces (ADR-0022's reasoning), contention at width 3 wastes gate runs, and the single lander is what serializes migration-touching lands.
- **Keep a draft PR per ticket for visibility.** Rejected as a default: every WIP push would trigger the repository's PR CI unless the project configures it to skip drafts — a repo-level change the loop cannot make — and the merge commit's `(#n)` plus the landing comment on the ticket give the ticket→commit trail the PR used to. Per-ticket PRs remain the single-ticket front door's mode, where the PR *is* the human review checkpoint.
- **Drop the per-ticket remote verifier** since the lander pushes first-hand. Rejected: it is a small-model dispatch, not a wall-clock cost, and "nothing is trusted from a report" (ADR-0005) is the property that made the field run's fifteen "done"s all true.
- **Skill mode as the lean engine** (an orchestrator session with a real shell doing merges itself). Rejected as the default: the workflow's script state surviving compaction is why it became the one engine (ADR-0022); the skill-mode exception performs the same landing steps in its own session, so the two frontends stay parallel.

## Consequences
- Easier: the two dominant overheads — the per-ticket cloud-CI wait and rebuilt work after a recycle — disappear; a fifteen-ticket campaign should take a small multiple of raw build time rather than a working day; the full suite is paid at most once per five lands; a relaunch after a recycle is minutes; migration tickets cannot collide; a long build is visibly alive on the remote. Per land, one lander and one small-model verifier replace a gate, several watchers, a recalled gate, and a verifier.
- Harder: the loop mutates the checkout it was launched from (it must be clean at launch and ends on the target branch at the landed tip); a project wanting a cheap fast gate must name `testing.checkCommand`; a red checkpoint can hold finished tickets until a human acts; a regression that only the full suite catches is found up to `checkpointEvery` lands later, at repair rather than rebuild cost; the `launch-ralph` skill and the workflow gained a landing procedure, checkpoints, `resyncs`, `checkpointEvery`, `knownGreen`, and `maxBuilds` to keep textually parallel.
- Constrained: no cloud CI runs before the release PR — projects whose CI does something a container cannot (matrix builds, secret-gated integration tests, deploy previews) get that signal at release, not per ticket; the release PR stays offered, never opened, so that CI run is a human's to trigger. Behavior is covered by tests that execute the workflow script against mock agents and assert the dispatch sequence: land under the fast gate with no gate/watcher dispatches; a conflict on land re-syncs without spending an attempt; bounded re-syncs; checkpoint cadence and the release skipping a proven tip; a red checkpoint repaired once, and held tickets plus an unverified run when the repair fails; the pool dispatching around a slow build; migration serialization; critical-path ordering; canary; deferral after a refresh; cap; branch adoption and `knownGreen`.

## Revisit when
- A consuming project's required CI proves something the local gate structurally cannot (platform matrices, secret-gated suites) often enough that a per-ticket cloud signal is worth its wait again — that would argue for an opt-in `gate: 'ci'` beside the local landing, not a return to it.
- Field data shows red checkpoints are common enough that one repair attempt is the wrong bound, or that `checkpointEvery: 5` localizes too coarsely or too finely.
- The harness lets a dispatched agent idle-wait cheaply — irrelevant to the local gate, but it would reopen the draft-PR-per-ticket question for visibility.
- The hosted environment stops offering a shared, warm checkout to land in (transport-level restrictions on pushing non-designated branches, or per-agent containers), which would push landing into the builders' worktrees and reopen the ownership question.
