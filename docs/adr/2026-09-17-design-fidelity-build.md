# Design implementation is a fidelity build against the committed prototype (`launch-design-implement`)

## Status
Accepted — amends [ADR-0024](0024-design-handoff-onramp.md): the design handoff on-ramp gains a fourth route, the *faithful build* of one canvas, and the handoff package gains a second project-owned file, `fidelity.md`; the on-ramp itself still routes and never builds. Amends [ADR-0018](0018-implement-front-door.md): `/launch-implement` stays the one door for *tickets*; a committed design package gets its own user-typed build command because its input, contract, and done-criterion differ — the ticket path reuses the same protocol rather than a second one. Extends [ADR-0034](0034-browser-smoke-one-off-driving.md): the browser smoke's "compare to a design only when named" is now defined — the named comparison is the fidelity protocol's side-by-side.

## Context
The design round trip ADR-0024 set up works: a Claude Design export dropped into the session becomes a committed package under `docs/design/<slug>/` — the prototype verbatim plus a distilled `handoff.md` — and the feature is sized onto the rail. Field use then showed the trip's other half, the *build*, missing the mark. The flow is the same every time: the user redesigns a page or designs a new one in Claude Design, iterates until it is right, exports a zip, drops it into Claude Code, names the canvas ("take the issue detail prototype and implement it"), and gets an implementation that resembles the design without being it. One platform's issue page was redesigned this way and the result was wrong enough to be redone from a second, more explicit prototype.

Six causes, each observed:

1. **Screenshots read instead of code.** A Claude Design canvas is a self-contained HTML file — real markup, real styles, a script that switches its screens and opens its modals. Implementers took values from an image of it and re-derived the layout, forfeiting exactly the precision the file carries.
2. **The first render built, the rest skipped.** One canvas holds a whole clickable prototype — tabs, sub-pages, drawers, modals, expanded rows, the empty and error variants the designer drew. Nothing enumerated those states before the build, so the ones behind a click were built loosely or not at all.
3. **The design normalized toward the product.** Existing components and tokens were reused because their names fit, and the prototype's values quietly moved to the nearest existing ones. The design system was never asked to change, so the design changed instead.
4. **No side-by-side at the approved size.** The user signs a canvas off at one viewport ("scaled to 1080p where I confirm it looks great"). Nothing put the prototype and the product next to each other at that viewport, so "looks right" was a judgment made from memory.
5. **The wrong canvas, chosen silently.** An export holds every canvas of the project — earlier iterations, sibling pages. The target lived in chat; the package recorded files, not which one was the subject.
6. **Data the prototype shows, dropped or faked.** A design draws content the product may not have yet (a captured request body, an assignee search). Without a rule, the element was omitted without a word, or filled with sample data in product code.

The rail's existing path — handoff → grill → spec → tickets → `/launch-implement` — is right for a *feature* a design opens. For a page whose prototype already *is* the specification (a redesign of an existing screen, a new page whose every state is drawn), it is ceremony: the spec would paraphrase the prototype, and the tickets would name it. ADR-0024 deliberately made the on-ramp "route, don't build", which left the direct build unowned — so it happened ad hoc, with the six failures above. ADR-0029 already gives a committed prototype authority as a decision record; what was missing is the discipline that turns that authority into pixels.

## Decision
- **A fidelity protocol defines "true to the prototype"** and lives in one file, `launch-design-implement/fidelity.md`: how to read a Claude Design export (one file per canvas; a canvas can be a whole prototype; values live in the code; the designed viewport); the **state inventory** — every reachable state found twice, by reading the script and by driving the prototype in a browser, each recorded with its click path and what in it must match, with the completeness rule that a drawn state not built is a deviation and an undrawn state is an open question, never an invention; the **token and component maps** — values map to tokens only under a handoff ruling, everything else ships verbatim and marked `raw`, components are reused only for an identical render, and the design system changes to carry the prototype rather than the reverse; the **data map** — every visible datum sourced, placeholder, or a recorded decision, never faked and never silently dropped; and the **side-by-side comparison** — two driver sessions at the same designed viewport, the prototype from its committed file and the product from the stack `launchrail dev` started, each state captured on both sides and looked at, measured with computed styles and boxes where the eye can't tell, with a fixed verdict vocabulary (`pending`, `match`, `deviation`, `accepted` with a concrete reason and who accepted it, `unverified`).
- **A new user-typed skill, `launch-design-implement`, builds one named canvas under it — in one invocation.** The user drops the export, names the canvas, and types the command; nothing runs before it. The skill composes `launch-design-handoff` to make the package on the way (the on-ramp keeps ownership of `docs/design/<slug>/`; it commits and returns without sizing or routing, its documenting questions batched into the build's one interview), or takes a package already committed; resolves the canvas (listed by title, matched to the user's words, asked when ambiguous), echoes canvas, viewport, product mapping, rulings, and branch once before any code, writes the contract — `docs/design/<slug>/fidelity.md`, every state `pending` — and commits it *before* the build so nothing is narrowed quietly, asks only what blocks a drawn state under the interaction contract, builds state by state from the prototype's own markup and styles (replacing the design it supersedes in the same change), compares each state as it lands, and closes only when every row is `match` or `accepted`, the gates are green, and the record is committed with the build. A build no browser could verify is reported as unverified, never as done. It carries `disable-model-invocation`: implementation is never started unprompted, so the on-ramp hands the command over exactly as it does `/launch-implement`.
- **The record is project-owned; the captures are not committed.** `fidelity.md` sits beside `handoff.md` — the handoff says what the design is and decides, the record says what was built against it and how it was proven — and is revised in place when the canvas is re-exported. Screenshots go under `.launchrail/state/design/<slug>/`, which ignores itself: they are regenerable from the committed prototype and the running product, and ADR-0034's no-evidence-bundle rule stands.
- **The on-ramp gains the faithful-build route and inventories interactive prototypes.** `launch-design-handoff` names the canvases in an export and records which one(s) the package is about and the designed viewport; when a canvas is an interactive prototype its screen inventory is the protocol's state inventory; and its routing offers the faithful build — `/launch-design-implement <slug> "<canvas>"` — beside tweak, feature, and redesign, choosing it when the prototype is the spec. Called by `launch-design-implement` to package a fresh drop, it commits and returns without routing.
- **The ticket path uses the same protocol.** `launch-ralph-implement` builds a ticket that names a design package under the protocol — inventory before code, the prototype's code as source, verdicts in the package's `fidelity.md` — and `launch-browser-smoke`'s named design comparison is the protocol's side-by-side. One definition of true, wherever a design gets built.
- The skill ships through the managed skill surface (`skillFiles()` walks the assets directory); the skills test pins the user-typed set at five.

## Alternatives considered
- **Fold it into `/launch-implement` as a design scope.** Rejected: the ticket door resolves numbers, labels, and an integration target and routes to the loop; a design build has a different input (a package and a canvas), a different contract (the protocol), and a different done (state parity, not acceptance criteria). One door with two shapes inside is the six-concepts wall ADR-0018 removed, rebuilt behind the door.
- **Require a ticket — put the protocol only in `launch-ralph-implement`.** Rejected: the user's flow has no ticket, a tracker-less project would need a local one to build a page, and the detour adds nothing the committed package doesn't already settle. The protocol *does* ride the ticket path; it is not gated on it.
- **Make the skill model-invocable so the handoff can flow straight into building.** Rejected: implementation is never started unprompted (ADR-0018, the conductor rules). The handoff prepares the command; the user types it.
- **Commit the reference and product captures as evidence.** Rejected: the prototype file is the durable reference and the record the durable verdict; images regenerate from both. ADR-0034 already declined a committed bundle for the smoke, for the same reason.
- **Automated pixel-diff with a threshold instead of a looked-at comparison.** Rejected for now: font rendering, anti-aliasing, and framework-generated DOM produce noise a threshold either hides or drowns in, and the judgment the check needs — is this the same design? — is visual. Computed styles and boxes give the numbers where the eye can't tell. Revisit below.
- **Paraphrase the protocol inside each skill that needs it.** Rejected: three copies of one contract drift; `workflow.md` already set the pattern of one normative file referenced by name.
- **Two invocations — file the package with the on-ramp, then type the build.** Rejected: the user's act is one ("here is the zip, build this canvas"), and a required first step is exactly the hand-driven sequence ADR-0024 removed from the sized path. The on-ramp stays the package's owner and is composed by the build; it remains a command of its own only for the sized paths, where the package is the input to planning rather than to a build.

## Consequences
- Easier: "take this canvas and implement it" is one command — the drop packaged on the way — with a written contract and a proven result — the user reviews a table of states and verdicts, not a feeling. The six observed failures each have a rule against them, and a build that skips one leaves a visible `pending` or `deviation` row instead of a silent gap.
- Harder: the build costs a state inventory and a per-state comparison up front — deliberately, since the alternative was a second prototype and a second build. The skill's own weight (a contract file plus a record) is the ceremony this needs and no more.
- Constrained: a second user-typed build command exists beside `/launch-implement`, for a different input; the skills test pins the set. `docs/design/<slug>/` carries two files per package. `.launchrail/state/design/` appears in projects that build designs — gitignored, like the rest of the state directory. The browser-testing module (a driver and Chromium) is the precondition for a *verified* build; without it the build is honest about being unverified.

## Revisit when
- Claude Design exports stop being self-contained HTML (a bundle format, an API) — the "reading an export" section of the protocol is what changes; the inventory and comparison stand.
- A visual-diff tool proves reliable across framework and font rendering — it becomes the first pass of §4, with the looked-at comparison kept for judgment.
- The faithful build turns out to be the dominant design-first path — reconsider whether the on-ramp should default to it and size only on request.
- A ticket-path build and a `launch-design-implement` build are observed diverging in rigor — the protocol needs enforcement in the record's shape, not more prose.
