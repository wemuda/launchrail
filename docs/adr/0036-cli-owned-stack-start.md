# ADR-0036: The CLI owns the smokeable stack's start contract; composed stacks are declared

## Status
Accepted — amends [ADR-0034](0034-browser-smoke-one-off-driving.md) (the browser smoke's start path, driver resolution, gate precondition and state directory) and [ADR-0004](0004-browser-testing-module.md) (`scripts/dev.mjs` becomes a delegating script like its siblings).

## Context
The first field run of the ADR-0034 skill, on a fresh hosted clone of a platform with an SDK, an API, a dashboard and a worker, succeeded only after the implementer abandoned the skill's start path and rebuilt the stack by hand. Everything the skill relied on was a contract stated in prose and implemented in seeded scripts: a start command, a URL file, a pid file, a port flag, an installed driver. Seeded files are project-owned by design and never updated by `sync`, so an adopted project's `dev.mjs` and `setup.mjs` were the old ones: no `--port`, no `dev.url`, no `dev.pid`, no `agent-browser`. The skill was out of contract in every adopted repository on the day it shipped, and nothing checked. Underneath sat a modelling gap: the skill assumed one process on one origin, while the smokeable surface was composed — several origins, a backend that needs a database, fixtures, an emailed sign-in link — and the project already had an in-process harness for exactly that, which the skill had no concept of. The run also found the gate precondition disproportionate (with no `checkCommand`, "fast" was a five-minute full suite), the driver failing with "Chrome not found" until pointed at Playwright's Chromium by environment variable, `--executable-path` silently ignored once a daemon runs, setup mentioned only as an aside although a hosted session is always a fresh clone, and `.launchrail/state/` left untracked files behind.

## Decision
- **`launchrail dev` owns the start contract.** A managed CLI command — `--background`, `--port <n>`, `--stop`, `--check`, `--timeout` — runs the project's start command, waits until every origin answers HTTP, and writes `.launchrail/state/stack.json` (origins, pid, log), `dev.url`, `dev.pid` and `browser.env`. The seeded `scripts/dev.mjs` becomes a delegating script like `verify` and `doctor`, so behavior updates with the toolchain; the skill calls the CLI directly, so an adapted copy in an older project can no longer put it out of contract.
- **Composed stacks are declared, not inferred.** The manifest gains an optional `smoke` block: `start` (the command that boots the whole smokeable stack) and `origins` (name → URL, each of which must answer). Without it, `dev` runs `testing.devCommand` and checks the single `app` origin at `testing.appUrl`. `stack.json` is a **merge** file: the start command adds what the smoke needs — keys, fixture ids, a mailbox path — and the CLI adds what it started; neither replaces the other. The pattern for booting a real backend in-process without Docker, stubbing only outbound seams, seeding fixtures directly, running the real frontends and relaying captured sign-in mail to a file ships as `composed-stack.md` beside the skill. It is documentation and a contract, not a generated harness: Launchrail cannot boot arbitrary backends.
- **The proof runs at adoption, not in a smoke.** `launchrail dev --check` starts, waits, asserts the state files, tears down and reports. `add browser-testing` names it as the first next step; `launch-loop-readiness` runs it in its inventory; `doctor` stays file-based (ADR-0033) and reports the resolved start command and origin count instead. A stack that `dev` cannot start is a **blocker** for the smoke — the implementer reports the gap and points at `composed-stack.md`; it does not rebuild the stack by hand inside a ticket.
- **The CLI resolves the driver's browser.** `browser.env` sets `AGENT_BROWSER_EXECUTABLE_PATH` to a Chromium found in this order: an explicit value, `PLAYWRIGHT_BROWSERS_PATH`, the hosted image's Chromium, Playwright's per-user cache — so the driver reuses Playwright's build and downloads nothing; and `AGENT_BROWSER_ARGS` turns the sandbox off in a root container. The env-var form is the documented one because `--executable-path` is ignored once a daemon runs. `setup.mjs` installs the `agent-browser` package only; `agent-browser install` remains the fallback where no Chromium resolves.
- **The gate is proportionate.** The standalone smoke runs `verify --fast` only when `testing.checkCommand` is set; otherwise it says so and runs without a gate. Inside a Ralph dispatch the fast gate already ran. `add browser-testing` is not gated on a check command.
- **Setup is step zero.** In a hosted session, or whenever `node_modules` is missing, `node scripts/setup.mjs` runs first, unconditionally. `verify` and `dev` detect a missing `node_modules` and name the install instead of surfacing the first command's "not found".
- **The state directory ignores itself.** `launchrail dev` writes `.launchrail/state/.gitignore` containing `*` before anything else lands there, so URLs, pids, logs and a throwaway driver script never appear as untracked files, and no project-owned `.gitignore` is edited. `doctor` warns when the directory exists without it.
- **Three driver notes enter the skill:** success toasts auto-dismiss, so confirm through the network result; prefer refs or role-based finds over text finds; refs are invalidated by navigation, so re-snapshot after `open` and reload.

## Alternatives considered
- **Have `doctor` start the stack.** Rejected: doctor proves what a file read can prove and never starts processes (ADR-0033); a doctor that boots servers would block conductors that treat "doctor green" as a cheap stage-0 check. The proof is its own explicit command.
- **Regenerate `dev.mjs` as a managed file.** Rejected: projects adapt it (the field project's ran `turbo run dev`), and managing it would either clobber those adaptations or conflict forever. Delegation keeps the file trivially theirs and the behavior Launchrail's.
- **Generate the composed-stack harness.** Rejected: which backend, database engine and mail seam a platform has is the platform's; Launchrail owns the contract (`smoke.start`, `origins`, `stack.json`) and teaches the pattern.
- **Require `testing.checkCommand` before enabling browser-testing.** Rejected: a tuning concern must not block adoption; readiness already warns, and a proportionate gate covers the actual problem.
- **Add `.launchrail/state/` to the project's `.gitignore`.** Rejected in favor of the nested ignore: it needs no edit to a project-owned file and holds even in a repository that never ran `init` again.

## Consequences
- Easier: the skill's start path is the same in every project and cannot drift; a platform with an existing full-stack harness is one wrapper script and one manifest block away from a working smoke; the driver needs no second browser download; a fresh hosted clone fails on the install, by name, not on `turbo: not found`.
- Harder: one more command and one more manifest block to keep honest; readiness for a composed stack is "each origin answers HTTP" — whether fixtures are in place is the start command's job, and the skill says so; `--port` re-addresses only the derived single origin, a composed start command owns its ports.
- Constrained: browser resolution knows Playwright's layouts and the hosted image's path; other browsers or layouts fall through to agent-browser's own download.

## Revisit when
- A consuming stack needs readiness richer than HTTP answering (a fixture probe, a seeded-user check) — `origins` could grow a per-origin readiness command.
- Hosted images move the pre-installed Chromium or Playwright changes its cache layout.
- Enough composed stacks share a database or mail seam to justify a seeded harness skeleton.
