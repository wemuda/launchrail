# ADR-0034: Browser smoke is one-off driving of the running stack; the e2e lane stays thin

## Status
Accepted — amended by [ADR-0036](0036-cli-owned-stack-start.md): the stack starts through `launchrail dev` (never an adapted seeded script), composed stacks are declared in the manifest's `smoke` block, the driver's browser is resolved by the CLI, and the gate precondition is proportionate. Amends [ADR-0004](0004-browser-testing-module.md) (the journey contract, the evidence bundle, the `smoke` command and the seeded Playwright MCP are retired; the Playwright baseline, `verify` and the semantic scripts stand). Where [ADR-0032](0032-ralph-lean-local-gate-loop.md) and [ADR-0033](0033-loop-readiness.md) say "browser journeys", read the Playwright e2e specs — the deterministic lane below.

## Context
ADR-0004 set up two complementary systems: deterministic Playwright e2e tests as the release gate, and agentic smoke testing as exploratory acceptance, driven from a Markdown catalogue of journeys and recorded in a committed evidence bundle. Two consuming platforms show what that contract produced in the field:

- One accumulated a catalogue. The seeded `docs/testing/smoke-journeys.md` said every user-facing ticket adds a journey there, and the `launch-browser-smoke` skill drove the *whole* catalogue on every run — so the cost of verifying one change grew with the age of the project, and the "variations worth trying by hand" the platform actually cared about lived in prose nobody drove.
- The other took the script fallback. The skill allowed "Playwright MCP, or a Playwright script — headless CI falls back to the scripts"; the Ralph loop runs hosted and unattended, which is headless, with a seeded `.mcp.json` that needs a one-time approval nobody is there to give. So every dispatch took the fallback, kept the script, and the seeded baseline spec's "extend or replace with real journeys as they stabilize" did the rest: a full-stack, in-process, real-browser Vitest suite named `smoke:platform` — a fine e2e test, and exactly the standing regression suite the agentic lane was meant *not* to be.

Both drifts were pointed at by Launchrail's own lines, and the loop already pays for them: ADR-0032's field data shows one required check running ~150 browser specs for 13–33 minutes per PR; ADR-0033's shows 161 serial specs run 30–40 times a night. Unbounded e2e growth is the dominant cost of the lean loop, not a stylistic preference. The vocabulary made it worse: "journey" meant a Playwright spec in ADR-0033 and a prose walkthrough in ADR-0004; "smoke" named both `tests/e2e/smoke.spec.ts` and the agentic run; the manifest carried a `smokeCommand` whose default was a script.

The owner's intent for the agentic lane was always narrower: implement a feature, then know how to bring the stack up and drive a real browser to see that the feature looks right and works — and move on. Not a run that re-runs on every future feature. Two facts about where the loop runs decide the mechanics: sessions are cloud-hosted and unattended (humans attend grilling, spec and tickets, then leave), and several builders run in parallel worktrees on one machine.

## Decision
- **Two lanes with honest names.** *e2e* is deterministic and thin: the Playwright specs under `tests/e2e/`, run by `launchrail verify` through `testing.e2eCommand`, entered only by decision — a standing golden path, or behavior only a real browser can exercise (a cross-origin opaque response, `sendBeacon`). *Browser smoke* is one-off: after building user-facing behavior, the implementer drives the running app in a real browser, judges what it sees, reports it in the handoff, and moves on. A smoke never becomes a spec by default, and a spec is never written from a smoke without the ticket asking for one.
- **The smoke's input is the change, not a catalogue.** Its steps come from the ticket's acceptance criteria and the diff — three to six of them, held in the implementer's head and handoff, never appended to a repository file. `docs/testing/smoke-journeys.md` is no longer seeded; a project's existing copy is theirs (the migration removes only an unmodified seed).
- **No evidence bundle.** The handoff's few lines on what was driven and what was seen are the record; the driving commands are the transcript. `launchrail smoke`, `artifacts/verification/`, `summary.md`/`deviations.md`/`meta.json`, `scripts/smoke.mjs` and `testing.smokeCommand` are retired. "Evidence over assertion" stands — an implementer still reports what it ran, and a smoke it could not drive is a failure, not a pass — at zero ceremony.
- **The driver is `agent-browser`, from the shell.** `scripts/setup.mjs` installs it (and its Chromium) next to Playwright; `doctor` warns when it is missing. Bash is the one surface every session has — hosted, unattended, inside a subagent — so no approval prompt stands between a dispatch and the browser, and `--session <name>` gives each parallel builder its own browser. Its accessibility snapshots with element refs are cheap on context, and `errors`, `console`, `network requests` and `screenshot` map one-to-one onto the standard checks. The seeded `.mcp.json` is retired: an MCP server is per session, so subagents would share one browser and one tab; `@playwright/mcp@latest` floats away from the pinned Chromium (the preflight refusal ADR-0033 recorded); and the approval it needs is never given in an unattended run.
- **Regression tests go to the cheapest seam.** A bug the smoke finds gets a unit or integration test first; a Playwright spec only when the ticket asks for one or the behavior exists only in a real browser.
- **Design comparison only when named.** The smoke compares the screen to a design (a `docs/design/` handoff, a mockup) only when the ticket or spec names one; it never invents the comparison.
- **The smoke is the implementer's, once per ticket.** `launch-ralph-implement` owns it for user-facing changes; the loop dispatches no smoke run of its own at release, and checkpoints stay purely deterministic. `scripts/dev.mjs` gains `--port <n>` (exposed as `PORT`) so parallel builders can each start the app, and records the URL and pid under `.launchrail/state/` (which ignores itself in git).
- **The fallback keeps its teeth.** Where `agent-browser` cannot be installed, the implementer writes a throwaway `playwright-core` script under `.launchrail/state/` — gitignored, never moved under `tests/` — and still looks at the screenshots.
- **Migration `2026-09-browser-smoke-one-off`** removes the retired seeds that are unmodified since Launchrail wrote them (`.mcp.json`, `docs/testing/smoke-journeys.md`, `scripts/smoke.mjs`), untracks a locally modified copy without deleting it, and strips `testing.smokeCommand` from the manifest with the usual comment-preserving round-trip. Existing `tests/e2e/smoke.spec.ts` files are left as they are (new projects seed `baseline.spec.ts`); existing `artifacts/verification/` bundles are the project's to delete.

## Alternatives considered
- **Keep the Playwright MCP as the primary driver, pre-approved through `.claude/settings.json`.** Pre-approval was solvable with the additive merge ADR-0021 uses; the shared per-session browser was not — parallel builders in one session would drive the same tab. Chrome DevTools MCP has the same shape.
- **A Launchrail-owned `scripts/browse.mjs` over `playwright-core`.** Rejected: it would reimplement a shell browser driver that already exists and is maintained — compose the runtime tools the workflow drives, own the skills the workflow is (AGENTS.md).
- **Keep the catalogue but scope each run to the changed journeys.** Rejected: the catalogue is the accumulation. Standing journeys worth keeping are exactly the e2e specs, entered by decision.
- **Keep the evidence bundle, uncommitted.** Rejected: the owner's record is the handoff; a scaffold nobody reads is ceremony ahead of need.
- **Keep `launchrail smoke` as a deprecation stub.** Rejected for the same reason; the migration removes an unmodified `scripts/smoke.mjs`, and a modified one prints the CLI's unknown-command error, which names the help.

## Consequences
- Easier: a user-facing ticket ends with the feature seen working in a real browser, by the agent that built it, in any environment that has a shell; the e2e suite stops growing as a side effect; the loop's full gate stays as small as the project decides; the vocabulary has one meaning per word.
- Harder: a smoke is non-deterministic and costs agent time — that is why it is bounded to once per ticket and never re-run at checkpoints; a second Chromium (agent-browser's) sits next to Playwright's; waits after actions are the driver's known sharp edge and the skill says so.
- Constrained: `doctor` only checks that the driver is declared; the skill's fallback carries the rest. Projects that turned smokes into specs keep them — they are e2e now, and their cost is theirs to weigh.

## Revisit when
- A hosted environment cannot install `agent-browser` at all (the fallback becomes the rule, or a different shell driver takes its place).
- Claude Code's own `run` skill or a session-level browser tool makes a seeded driver redundant.
- A consuming project needs the smoke to leave a durable artifact (a PR comment with screenshots would be the shape, not a committed bundle).
