# Operational guidance the toolchain must keep current is managed, not seeded — and a migration heals what shipped seeded

## Status
Accepted — amends [adr-date-slug-identifiers](2026-09-11-adr-date-slug-identifiers.md): the dated-identifier scheme reached new repositories through the seed, but not the repositories already carrying the old seeded guidance. This record adds the missing propagation path and the ownership rule that makes it safe. The registry, the reading contract, and the generated index all stand.

## Context
[adr-date-slug-identifiers](2026-09-11-adr-date-slug-identifiers.md) replaced the ADR sequence number with a coordination-free `YYYY-MM-DD-slug` identifier and a generated index. It changed three things — the scanner, the `launchrail adr index` command, and the seed strings `init` writes — and it stated that repositories initialized earlier "receive the new rules through the managed surfaces… and can adopt the generated table by running `launchrail adr index` once; their seeded registry text keeps its old wording until they edit it."

That last clause turned out to be live-fire, not a cosmetic lag. A consuming repository reported that its `docs/adr/README.md` still said **"take the next free number"** — the pre-date-slug guidance Launchrail itself seeded (ADR-0031 era) — and that agents were following it: `master` had merged an `ADR-0053` that collided with an in-flight branch, and a third `0053` was open in another PR. The instruction that the dated scheme exists to retire was still being handed to agents, verbatim, by a file Launchrail wrote.

Three facts explain why nothing fixed it, and together they frame the decision:

1. **The registry is a *seeded* file, and `sync` never rewrites seeded files** ([ADR-0006](0006-sync-engine.md)/[ADR-0031](0031-adr-registry-and-reading-contract.md)). That is a safety rail, not a gap — `sync` reconciles *managed* files and leaves *seeded*/*project-owned* ones alone. The date-slug ADR reaffirmed it, rejecting "regenerate the index from `sync`" for exactly this reason.
2. **`launchrail adr index` only rewrites the table between the markers.** It never touches the "Maintaining this registry" prose where the numbering instruction lives, and on a truly old registry (no markers) it introduces them but still leaves the prose.
3. **`doctor` is read-only.** It warns on duplicate ids and a stale table; it cannot correct anything.

So the forward fix had no propagation path into existing repositories, and the one instruction most needs to be correctable — *how an agent mints a record* — was sitting in the one class of file the toolchain had promised never to rewrite. That is the root cause: an operational instruction the toolchain must be able to keep current was authored only in project-owned surfaces.

## Decision
- **Operational guidance the toolchain must keep current is authored in a managed surface.** The authoritative ADR-minting contract (name by date and slug, no number to claim, declare relations forward, regenerate with `launchrail adr index`, legacy `NNNN-` records keep their names) now lives in the managed `.launchrail/CLAUDE.generated.md`, which `sync` rewrites every version. The seeded registry and template keep a **project-owned summary** and say, in one line, that the managed contract is what holds if the two ever disagree. The durable invariant may be summarized in a seeded file; the mutable mechanics have exactly one home the toolchain owns.
- **A one-time migration heals what already shipped seeded.** `2026-09-heal-adr-minting-guidance` rewrites the pre-date-slug "Maintaining this registry" section and the `# ADR-NNNN:` template — but **only when the text is byte-for-byte the version Launchrail seeded** (both were byte-stable from ADR-0031 until the dated scheme, so the match is exact). A section a project has edited, or a path it has ejected, is theirs and is left untouched; the migration reports nothing and changes nothing for it. This is the sanctioned surface for a structural change to a seeded file: ordered, idempotent, dry-runnable, recorded in the lockfile, recoverable — everything `sync`'s managed-file pass is not allowed to be for a project-owned file.
- **Two write surfaces, kept distinct.** The generated index table stays owned by `launchrail adr index` — a continuous, explicit, reviewable write the operator runs and commits. The one-time correction of stale seeded *prose* is a migration — a structural write recorded once. `sync` runs the migration, then regenerates the managed surface, then leaves the seeded file alone; a healed repo runs `adr index` to complete the table. Neither surface does the other's job.
- **Existing duplicate records are not auto-renamed.** Renaming a numbered record that external seeded files and hundreds of references cite by number is precisely what ADR-0031's "never renumber" rule and the date-slug ADR forbid. `doctor` instead names every file that claims a shared id and prescribes the safe resolution — give the newer collider a dated `YYYY-MM-DD-slug.md` name, which cannot collide. The rename stays a reviewed action in the consuming repo.

## Alternatives considered
- **Regenerate the seeded registry from `sync`.** Rejected again, for the reason the date-slug ADR gave: `sync` writing a seeded file blurs the ownership classes the safety rules protect. A one-time, recorded migration keeps the write explicit and bounded; a continuous reconciler does not.
- **Overwrite the whole registry (or template) in the migration.** Rejected — the registry mixes generated table, project-owned live picture, and doctrine in one file; a blanket overwrite destroys the project's own content. The migration matches and replaces only the one section, and only when it is unmodified.
- **Anchor on the phrase ("next free number") instead of an exact match.** Rejected — a fuzzy match risks rewriting a section a project authored that happens to mention numbering, violating the ownership model. Exact-match heals what Launchrail wrote and no more; anything else is reported and left for a human. The safe failure (a divergent section is skipped, and `doctor` still flags the symptom) is the right one.
- **Leave it as a manual chore (the status quo the date-slug ADR chose).** Rejected — the field report is the evidence that stale *instruction-bearing* seeded text is not passive. A seeded file aging cosmetically can wait for the project; a seeded file handing agents the wrong rule cannot.
- **Auto-rename the colliding records.** Rejected — breaks external links and violates never-renumber. Detection plus a prescribed safe rename is the toolchain's lane; the edit is the project's.

## Consequences
- Easier: a repository seeded before the dated scheme heals on its next `launchrail sync`, with no hand-editing and no risk to its own content; `doctor` already lists the pending migration, so the prompt to sync is automatic. Future changes to the minting mechanics propagate through the managed surface to every repo, with no new staleness.
- Harder: the registry's maintaining prose is now a *summary* that defers to the managed contract, so a reader wanting the full, current rule follows the pointer. The migration recognizes only the exact pre-date-slug text; a project that had already hand-edited that section keeps its wording (the managed contract still carries the truth, and `doctor` still flags any resulting duplicate).
- Constrained: instruction-bearing guidance that the toolchain must keep current may no longer live *only* in a seeded or project-owned file — it is authored in a managed surface, and any seeded copy is a summary that names the managed surface as authoritative. This is the ownership discipline the whole toolchain already follows, made explicit for guidance text.

## Revisit when
- A second class of seeded, instruction-bearing text goes stale in the field — the signal to generalize "heal an unmodified seeded section" from a bespoke migration into a small shared helper (a seeded-section reconciler), rather than writing a new exact-match migration each time.
- Duplicate numbered records become common enough that a prescribed manual rename is not enough — the signal to build an assisted, link-updating rename command, still operator-driven, never an automatic renumber.
