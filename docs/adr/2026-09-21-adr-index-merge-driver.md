# The generated ADR index auto-resolves parallel merges via a Launchrail-installed git merge driver

## Status
Accepted; extends [adr-date-slug-identifiers](2026-09-11-adr-date-slug-identifiers.md): the dated identifiers made the record *files* merge cleanly and made the index a deterministically regenerable artifact; this record makes the *generated index* merge cleanly too, closing the one conflict the dated scheme left behind. The generated table, the scanner, and the `launchrail adr index` command all stand.

## Context
[adr-date-slug-identifiers](2026-09-11-adr-date-slug-identifiers.md) gave every record a coordination-free `YYYY-MM-DD-slug` name, so two branches never pick the same filename and the `.md` records merge cleanly. It did **not** solve the file that is regenerated *from* those records: `docs/adr/README.md`. Each branch runs `launchrail adr index`, which appends a row near the bottom of the date-sorted table between `<!-- adr-index:start -->` and `<!-- adr-index:end -->`. Two branches insert different rows at the same anchor with identical surrounding context, so git's line-based 3-way merge cannot order them and emits a textual conflict — every time two branches add an ADR in parallel.

A consuming repository (fixback) hit exactly this merging `master` into a feature branch: a clean record corpus, but a conflict inside the generated table. The conflict carries no real disagreement. The table is a pure derived artifact whose source of truth — the records — merges fine, and it can always be rebuilt deterministically with `launchrail adr index`. A derived artifact that can be regenerated should never land a conflict on a human.

Two facts about *when* git resolves the file shaped the design, and both were verified empirically before building anything:

1. **git resolves content before it updates the working tree.** With merge-ort (git ≥ 2.34, the default), when git invokes the merge driver for `docs/adr/README.md` the *incoming* side's new record files are not yet on disk, nor in the index — only the three versions of the conflicting file itself (`%O` base, `%A` ours, `%B` theirs) are guaranteed available. So a driver that just runs `launchrail adr index` against the working tree would silently drop the other branch's new row. The records must be read from git, not from disk.
2. **A merge driver is named in committed `.gitattributes` but *defined* in per-clone git config.** The binding travels with the repo; the definition does not. A fresh clone therefore has the binding but no driver, and git falls back to the default line merge — the original conflict. Something that runs per clone must register the definition, with zero per-developer configuration.

## Decision
- **Resolve the file by regeneration, behind a named git merge driver.** `docs/adr/README.md` is bound to `merge=launchrail-adr-index`. The driver regenerates the index table from the merged record corpus and writes the result to git's destination (`%A`), instead of line-merging the rows. Everything outside the table is a genuine 3-way merge (`git merge-file` over the file with the index region reduced to a stable placeholder), so prose edits merge normally and a real prose conflict still surfaces for a human — only the generated table is ever auto-resolved.
- **The driver is a subcommand of the same package as the generator.** `launchrail adr merge-driver %O %A %B %P` ships in `@wemuda/launchrail` alongside `launchrail adr index`, so the driver and the generator are the same version by construction and can never drift in format — the failure mode a hand-rolled driver copied into each consumer repo would invite.
- **The merged corpus is read from git, not the working tree.** The driver reads the records from a real 3-way merged tree (`git merge-tree --write-tree` of `HEAD` and the incoming commit), so records the incoming side *adds* and records it *modifies* (a new ADR that supersedes and re-statuses an older one) both resolve exactly as the finished merge will. The output is byte-identical to `launchrail adr index` over the completed merge, so `launchrail adr index --check` stays clean in CI. On older git without `--write-tree`, it falls back to this side's working tree plus the records only the incoming side adds — correct for the additive case, which is the one the scheme is built around.
- **Install in two halves, matched to the two homes.** The committed `.gitattributes` line is managed additively (a project's own attribute rules are kept, only the one line is added) by `init` and by a one-time migration (`2026-09-adr-index-merge-driver`) for repos initialized earlier. The per-clone git config is registered by `init`, `sync`, and `doctor` — never behind the lockfile-recorded migration, because that runs once whereas every clone needs the definition. `doctor` reports the binding and **repairs** the per-clone config, so a fresh clone that runs the normal setup/doctor gets a working driver with no hand configuration.
- **Fail safe, never corrupt.** If anything goes wrong, the driver leaves the file untouched and reports a conflict, so git falls back to the documented manual step (`launchrail adr index && git add docs/adr/README.md`) rather than writing a damaged file. The same one-liner is the manual workaround on a clone that has not yet registered the driver.

## Alternatives considered
- **The built-in `merge=union`.** Rejected, and called out as a non-goal: it concatenates both sides' rows in arbitrary order, breaking the canonical date-sort and then failing `launchrail adr index --check` in CI. It also cannot recompute the relation back-references a new record induces in the rows of the records it supersedes or amends. Regeneration is the only resolution that matches `adr index`.
- **Regenerate against the working tree (what the file's records look like "already merged").** Rejected because it is wrong under the default merge strategy: merge-ort has not written the incoming side's new record files to disk when the driver runs, so the regenerated table would be missing the other branch's rows. Proven with a scratch merge before committing to the git-tree approach.
- **A hand-rolled driver script committed into each consumer repo.** Rejected — it would drift from the generator's format the first time either changed, and every consumer would carry and maintain a copy. Versioning the driver *with* the generator, in one package, removes the drift by construction.
- **A `post-merge` / `pre-merge-commit` hook instead of a merge driver.** Rejected — hooks do not fire on the rebase conflict path, and a clean-but-non-canonical auto-commit would still need an amend; the driver is the one mechanism that runs on both `git merge` and `git rebase` at the moment the file is resolved.
- **Leave `doctor` read-only and only report the missing driver.** Rejected — the per-clone config is exactly the state a fresh clone lacks, and a report that still requires a manual `git config` fails the "zero per-developer configuration" goal. Registering a local merge driver is safe, idempotent, and never touches committed history, so `doctor` repairs it; the committed `.gitattributes`, which *is* history, it only reports.

## Consequences
- Easier: parallel ADR work stops producing index conflicts. Two branches each add a record, regenerate, and merge or rebase with both rows landing in canonical order and no human step. The fix reaches existing consumers on their next `launchrail sync` (the `.gitattributes` migration) and `launchrail doctor` (the per-clone config), with nothing to change in the consumer repo by hand.
- Harder: resolving the index now depends on a per-clone git config that a bare `git clone` does not set. The gap is closed by `init`/`sync`/`doctor`, documented in the seeded registry and the managed workflow instructions, and papered over by a fail-safe that degrades to the old manual one-liner — but a clone that runs none of those, then merges, still sees the original conflict.
- Constrained: `docs/adr/README.md` is now a driver-owned file for its index region. Its generated table must stay a regenerable projection of the records — the property the driver relies on — so nothing may hand-author rows the records do not imply. The prose around the table stays the project's, merged normally.

## Revisit when
- A second generated, committed artifact starts colliding the same way — the signal to generalize "a version-matched merge driver that regenerates a derived file" from this one binding into a small shared install helper, rather than wiring each file by hand.
- `git merge-tree --write-tree` becomes a safe universal assumption (or a floor git version is adopted) — the signal to drop the working-tree fallback and read the merged corpus one way only.
- The driver's fail-safe conflict is observed landing on humans in the field — the signal that the per-clone registration is not reaching real clones, and that a more automatic install path (a checked-in bootstrap, or a `git config` in the setup hook) is warranted.
