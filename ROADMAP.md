# Launchrail roadmap

> Living document — the public answer to "what exists, what's in progress, what's missing." Update it in the same commit as the work it describes.

## Current status

All six phases are implemented; one real-world dogfood run remains open (phase 6's case study — it needs a real project, not this repo). Phase 4's Ralph loop has now run for real: it first ran against a real Wemuda project, and the run-earned mechanics were promoted back into both frontends (deterministic verbatim edge parsing, a dependency gate whose deferrals don't burn attempts, stricter remote verification, field-tested defaults, and a supervision contract for workflow runs — ADR-0010). Open-source readiness is in place: MIT license with generated output unencumbered (ADR-0007), getting-started guide plus a committed `init`-output example, CONTRIBUTING/SECURITY policies, CI and release-please release automation with a Conventional-Commits changelog (ADR-0008; npm publish activates once `NPM_TOKEN` and the npm org exist, see docs/releasing.md), and dated brand due diligence with pre-launch actions (docs/brand-due-diligence.md). `launchrail init` and `launchrail doctor` work on blank and existing repositories (interview or `--yes`, `--dry-run`, idempotent re-runs, checksum-tracked lockfile), and `init` ends by installing every Claude plugin the workflow depends on — Launchrail's own and Matt Pocock's skills — via the `claude` CLI when present (ADR-0011) and handing off into Claude Code (commit, run `/launchrail:launch`) — fixes promoted back from smoke-testing the onboarding on a real project, where the declared plugin's install prompt never fired for an already-trusted folder and the conductor stalled on upstream skills the user had never heard of. The Claude plugin carries the core workflow — a `launch` orchestrator skill that detects a project's stage and routes to the stage's owner (ADR-0009), the `vision-creation` and `design-validation` skills, a stage-by-stage workflow doc composing Matt Pocock's grill/research/spec skills, and plugin subscription via a project-scoped `.claude/settings.json` declaration (ADR-0003) — plus `browser-smoke`. `launchrail add browser-testing` seeds the browser-testing module (Playwright baseline, semantic scripts, smoke-journey contract, ADR-0004) with `launchrail verify` and `launchrail smoke` as the verification surface. `launchrail add ralph` installs the Ralph loop: the `ralph`/`ralph-implement`/`resolving-merge-conflicts` skills in the plugin plus a managed `.claude/workflows/ralph.js` workflow, verification-gated end to end (ADR-0005, field-revised by ADR-0010). The sync engine (ADR-0006) keeps older projects current: `status`, `diff`, and `sync` share the safe writer's plan, migrations are ordered and idempotent, and `eject` provides vendor mode — the managed Ralph workflow receives updates through it. Adopting a mid-development project is a first-class path: `init` additively prepends the two workflow `@`-imports to an existing `CLAUDE.md` (ADR-0012), keeping the file otherwise untouched, and `doctor` checks both imports so the managed workflow instructions can't be silently orphaned. The interview now asks whether the project is new or existing (defaulting to `existing` when it detects a `package.json` or agent files), records it as the manifest's `origin`, and for an existing project `launch` takes the alignment on-ramp — the `project-alignment` skill inventories the codebase, infers a draft vision, interviews only the gaps, and detects the existing design system before handing to `vision-creation` (ADR-0013), instead of starting from a blank vision. 164 tests, including integration tests against temporary git repositories. Nothing is published to npm.

## Phase 1 — `init` + `doctor`

**Goal:** `npx @wemuda/launchrail init && npx @wemuda/launchrail doctor` works on a blank repo and a realistic existing repo without destroying local files.

- [x] `.launchrail.yml` manifest schema and the ownership model (managed / seeded / project-owned)
- [x] `.launchrail-lock.json` lockfile (versions, checksums, applied migrations)
- [x] Safe file writer: dry-run, checksum tracking, idempotent re-runs
- [x] New/existing repository detection (package manager, stack, git remote, existing agent files)
- [x] Init interview: project mode (spike / standard MVP / high-rigor), issue tracker, Conventional Commits (ADR-0002), test commands
- [x] Seed `AGENTS.md` + `CLAUDE.md` arrangement without overwriting existing content; chosen conventions (commit format, commands, definition of done) are written into the seeded `AGENTS.md`. A pre-existing `CLAUDE.md` is kept but additively wired to the two workflow `@`-imports so the managed instructions are never orphaned ([ADR-0012](docs/adr/0012-init-wires-imports-into-existing-claude-md.md))
- [x] Seed ADR conventions (`docs/adr/` + template)
- [x] Matt Pocock skills installation guidance and setup detection
- [x] `doctor`: baseline repository and environment checks
- [x] Fixture and integration tests against temporary git repositories

## Phase 2 — Core workflow plugin

**Goal:** a fresh project can move from idea to an approved MVP spec through committed artifacts. Launchrail composes Matt Pocock's skills wherever one already covers a stage — no duplicate skills.

- [x] `vision-creation` skill
- [x] Complexity grill: reference and integrate Matt Pocock's `grill-with-docs` (setup guidance + workflow docs, no custom skill)
- [x] Technical research: reference and integrate Matt Pocock's research skill, fed by the project's grill constraints
- [x] `design-validation` skill (spec → Claude Design → revised spec → handoff)
- [x] Plugin installation through a project-scoped declaration (`.claude/settings.json`, ADR-0003)
- [x] `launch` orchestrator skill — one entry point that detects a project's stage from committed artifacts and routes to the stage's owner, jumps to a named stage (e.g. `deep-research`), and asks when the read is ambiguous (ADR-0009)
- [x] `start-feature` conductor — a sibling to `launch` for the per-feature delivery loop on an already-founded project: size a feature (large / semi / small) and route it through the matching planning subset, then hand off to the Ralph loop; composes the stage owners, never reimplements them (ADR-0014)

## Phase 4 — Ralph release orchestration

**Goal:** Ralph implements a small example MVP and cannot declare success while required verification fails.

- [x] Integrate the Wemuda-provided Ralph skill (supplied, not written from scratch) — adapted as the plugin's `ralph` orchestrator skill plus the named contracts it dispatches to (`ralph-implement`, `resolving-merge-conflicts`)
- [x] Integrate the Wemuda-provided campaign workflow script — `launchrail add ralph` installs `.claude/workflows/ralph.js` as a managed file; policy overrides via workflow args, config discovered at run time (ADR-0005)
- [x] Completion contract, max iterations, blocker reports — per-ticket contract in `ralph-implement`; retry-once-then-park with `needs-info` + failure history; `maxRounds` backstop; stuck tickets reported with their blockers
- [x] Verification-gated completion and release evidence summary — `launchrail verify` gates preflight, every ticket, and campaign close-out (plus browser-smoke evidence when the module is enabled); a red or empty gate refuses to start, a red final gate reports "unverified"
- [x] Dogfood: first real Ralph campaigns run against a real Wemuda project (a real repo beat the planned example MVP); the run-earned lessons are folded back into both frontends (ADR-0010)

## Phase 5 — Sync engine

**Goal:** an older project receives new skills and renamed capabilities without losing local product knowledge.

- [x] `status` — drift, available updates, pending migrations, upstream advisories
- [x] `diff` — preview upstream changes as unified diffs
- [x] `sync` — safe initial subset ([ADR-0006](docs/adr/0006-sync-engine.md)): checksum-gated managed updates, conflicts keep local edits; generated content updates whole-file via `.launchrail/CLAUDE.generated.md` (true three-way merge deferred until base content is stored)
- [x] Versioned, ordered, idempotent, dry-runnable migrations (in-CLI registry, recorded in the lockfile, failure leaves the repo recoverable)
- [x] Upstream dependency compatibility tracking — advisory rename registry scanned against project docs (registry empty until the first real upstream rename)
- [x] `eject` / vendor mode (`eject <file|module>`, `eject --all`; ejected paths are never written again)

## Beyond 1.0 — candidate directions

> Unscheduled and uncommitted — real gaps and expansion ideas kept here so they get weighed deliberately instead of forgotten. None of this is ceremony ahead of need; each item graduates into a phase (or an ADR that rejects it) only when a real project demands it.

- **Close the promotion loop.** The updatability model promises "reusable lessons are deliberately promoted upstream," but today that is a habit, not a mechanism. Candidate: a documented promotion path (a CONTRIBUTING recipe, or eventually a `launchrail promote` helper) for lifting a project-grown skill or convention into the toolchain.
- **True three-way merge for generated content.** `sync` updates generated content whole-file; storing base content in the lockfile would enable real three-way merges (explicitly deferred in ADR-0006).
- **Upstream compatibility watch.** The rename-advisory registry is empty while Matt Pocock's skills keep evolving. A scheduled CI job that diffs upstream skill names and contracts against `plugins/launchrail/docs/workflow.md` would catch drift before consuming projects do.
- **Command-surface audit before 1.0.** Nine commands with adjacent diagnostics (`status` vs `doctor`, `verify` vs `smoke`) — before the CLI surface freezes at 1.0, confirm each earns its place or fold overlapping ones.
- **Editor/vendor breadth.** AGENTS.md is vendor-neutral but the plugin is Claude Code–only. Decide deliberately whether other agent runtimes are a goal or a non-goal, and record the answer as an ADR either way.
- **Case study as launch artifact.** The phase-6 dogfood case study doubles as the primary public evidence at announcement time — worth writing for readers, not just as a checkbox.

## Landed

- [x] 2026-08-11 — Conductor guidance fixes from a real spec-stage dogfood run: (1) stage 7 (design validation) is now a judgment scaled to the spec's design surface, not a mechanical turnstile — an API-/schema-heavy spec gets routed on to tickets with validation offered as a quick pass over its few screens or a recorded skip, and a recorded skip still writes the `## Design validation` section so the stage-8 gate stays artifact-based (`launch`, `design-validation`, workflow doc); (2) `launch`'s "always leave a map" now requires explaining what the next stage *does* and whether it is optional, then showing the arc to the destination (spec → validation if UI surface → tickets → Ralph loop → verification) — a bare "next is stage 7, design validation" left a user unable to tell pre-ticket spec QA from post-implementation review; (3) `ready-for-agent` is documented as a ticket-only label at every surface the loop touches — a spec issue published to the tracker wearing it enters Ralph's frontier and gets dispatched as work, so the `ralph` skill's preconditions stop-and-relabel, and the ralph workflow's graph stage excludes plainly-non-ticket issues via a `notTickets` report and logs the labeling error instead of building it (`launch`, `start-feature`, `workflow.md`, `ralph` skill, `ralph.workflow.js`).
- [x] 2026-08-10 — `start-feature` conductor: a sibling skill to `launch` that drives the per-feature delivery loop on an already-founded project. It frames a feature, sizes it (large / semi / small), and routes it through the planning subset that size needs — wayfinder / grill / to-spec / design-validation / to-tickets, calibrated by the manifest `mode` — then hands off to the Ralph loop and verification. - [x] 2026-08-10 — Renamed the implementation capability from **Ralph campaign** to **the Ralph loop** across every living surface — the `ralph`/`ralph-implement`/`resolving-merge-conflicts`/`launch` skills, plugin and marketplace descriptions, the managed `ralph.js` workflow (meta, prompts, comments), CLI output, and the seeded `CLAUDE.generated.md` heading (`## The Ralph loop`), which reaches existing projects on `launchrail sync` since generated content updates whole-file (ADR-0006). The stage-3 map row now says "never the bare `grilling` primitive" and a new note explains why, closing the "the interview looked fine" trap.
